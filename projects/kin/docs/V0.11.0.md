# v0.11.0 — Durable Service & Deployment

**Status:** Planned. No v0.11 implementation, persistent server schema, or
deployment guarantee is present.

## Prerequisites

- Human review and closure of the v0.10.x local architecture/security gate.
- Preserve the existing minimum-knowledge service boundary and encrypted
  envelope/canonical event contracts unless a separately reviewed change is
  necessary.

## Problem being solved

The current identity service and encrypted relay are process-memory only.
Ordinary restart loses identity, authorization, provisioning/rotation state and
accepted relay envelopes. A process-local acceptance must not be described as a
durable acknowledgement.

## Scope

Plan and implement durable, restart-safe handling for at least:

- households and memberships;
- WebAuthn credentials and public credential state;
- trusted devices, public key/fingerprint history and revocation;
- sessions only where persistence is intentional and safe;
- encrypted event envelopes, identity/idempotency records, relay cursors and
  high-water marks;
- identity bindings, key-epoch coordination, rotation proposals and provisioning
  grants;
- rate-limit/security state when restart would otherwise weaken its policy.

Explicitly identify which pending flows, challenges and other transient records
must expire or be discarded at restart. By default, discard outstanding WebAuthn
challenges, unclaimed pairing/claim flows, one-time ceremony state and
unauthenticated partial requests; require a fresh authenticated ceremony after
restart. A transient that must survive needs bounded expiry, one-time use and a
documented authorization reason. Do not persist secrets unnecessarily.

The release must define a separate server persistent-schema version and controlled
migrations. Required properties include atomicity where needed, uniqueness,
crash recovery, bounded queries, backup/restore, local self-hosted development,
low operational complexity, suitable Node integration and privacy-safe storage.
Evaluate embedded transactional storage (including SQLite) against those
properties before selecting a backend; do not add distributed infrastructure
without demonstrated need.

Define the external deployment boundary: HTTPS/TLS, configured trusted origin,
secure cookies, reverse-proxy expectations, startup validation, data location
and permissions, backup/restore procedure, graceful shutdown, health/readiness,
resource limits and structured privacy-safe logs. Forwarded headers are not
trusted by default. Do not add Kubernetes/cloud orchestration without need.

## Non-goals

- Turning the service into the household source of truth or a plaintext event
  reducer, analytics/search backend, mutable household document store or AI
  processor.
- Persisting private content keys or credentials when a public/opaque form is
  sufficient.
- Prematurely selecting a database before requirements/concurrency evaluation.
- Cloud/distributed operations, broad product features or UX redesign.

## Architecture boundaries

The service remains the authorization authority, trusted-device/membership
registry, opaque encrypted-event relay and cursor/provisioning/rotation
coordinator. Clients retain plaintext household semantics, content keys and
canonical event replay. Server migrations are independent of application, event,
WASM protocol, IndexedDB, sync-envelope and archive versions.

## Primary invariants

> Acknowledgement of authorized encrypted state means the accepted opaque
> envelope/state has been durably committed according to the documented
> durability contract.

Restart must not turn an acknowledged write into a false acknowledgement.
Duplicates remain idempotent across restart; authorization, revocation, epoch and
membership decisions remain coherent. Migrations fail closed and never silently
drop ciphertext. The service never receives plaintext household event content.

## Expected failure scenarios

Exercise abrupt process termination during event, provisioning and rotation
commits; restart after acknowledgement; duplicate retry after restart; revoked
device restart; partial/corrupt database; migration interruption/failure; backup
restore; full disk/quota/resource exhaustion; invalid deployment configuration;
shutdown during active writes; proxy/origin mismatch; and stale or expired
transient flows.

## Acceptance/readiness criteria

- A versioned server schema and explicit migration/rollback/backup contract are
  documented independently of all other version axes.
- Integration tests prove event envelopes, idempotency, cursors, membership,
  device revocation and rotation/provisioning state survive process restart.
- An acknowledged event remains retrievable after service termination/restart;
  duplicate retries stay idempotent and do not partially commit.
- Migration and restore tests fail closed without losing ciphertext or weakening
  authorization.
- Startup rejects unsafe/misconfigured external origins; TLS/proxy expectations,
  permissions, health/readiness and shutdown behavior are documented and tested.
- Limits and logs do not reveal plaintext household content or secrets.
- No independent security audit, production certification or deployment support
  is claimed without evidence.

## Deferred decisions

Database backend, exact server schema, per-record retention, backup cadence and
operational packaging remain implementation decisions after requirements,
concurrency and failure testing. Security-sensitive choices require review.

## Relationship to next release

v0.11 establishes durable service semantics. v0.12 depends on knowing which
primary and backup records the service controls so household deletion and
retention promises can be precise.

## Proposed cadence

```text
v0.11.0 — Durable Identity & Relay Foundation
v0.11.1 — Restart / Migration Correctness
v0.11.2 — Operational Resilience & Deployment
v0.11.3 — Service Security / Privacy Hardening
```

These are planning candidates, not promises to manufacture four patches.

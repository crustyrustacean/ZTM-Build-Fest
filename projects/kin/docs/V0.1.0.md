# v0.1.0 — Household Heartbeat

**Status:** implementation specification only. Do not interpret this document as shipped functionality; no application code has been written.

## Goal

Prove one complete local household-item loop: add an item, persist its event, complete it, reload the page, and reconstruct the same current state from the event history. Keep the scope small enough to validate the Rust/WASM and browser boundary before adding household features.

## Rust responsibilities

Rust is the authority for the initial domain model and deterministic state behavior. Its domain event names and replay rules are specified in [EVENTS](EVENTS.md) and [STATE](STATE.md); the browser/WASM transport contract is finalized by the later v0.0.6 planning release. Rust will own:

- The minimal event representation and `ITEM_ADDED` / `ITEM_COMPLETED` handling
- Input validation and event validity checks
- State transitions and reconstruction by replaying events
- A result representation suitable for the JavaScript bridge

Rust must not access or manipulate the DOM, IndexedDB, WebAuthn, Web Crypto, or network APIs. The exact serialization and ABI are specified before implementation in the v0.0.6 ABI and implementation contracts. This document does not define a separate wire format.

## JavaScript responsibilities

JavaScript will own:

- Loading and initializing the WASM module
- The browser UI bridge and user interaction
- Persisting and retrieving the event history with IndexedDB
- Passing event data into Rust and rendering the derived state
- Browser lifecycle and accessible interactions

JavaScript must not independently implement the authoritative event replay or household-state transitions. It may provide immediate UI feedback, but Rust determines accepted events and resulting state.

## Web Components

The first custom element should be:

```html
<kin-app></kin-app>
```

A focused `<kin-item>` or `<kin-compose>` may be introduced if it removes meaningful complexity, but do not split the first screen into components without a concrete need. No component code is part of this planning release.

## Persistence and identity

Use IndexedDB as the likely local persistence mechanism for the event history. Define the smallest schema needed for this release and handle load, append, and reconstruction. Persistence must survive a page refresh in the supported browser.

Use a temporary local actor identity only. Do not implement partner accounts, household pairing, passkeys, authentication, remote sync, or a backend in v0.1.0.

## Initial event types

Only these domain event kinds are in scope:

```text
ITEM_ADDED
ITEM_COMPLETED
```

An added item needs only a stable item ID and text. Events also carry stable event, household, actor, and device IDs, a UTC timestamp, a local logical-order value, an event kind, and an event schema version; identity values are local placeholders, not real accounts or trusted devices. The local event store's append order is authoritative in v0.1.0. Wall-clock timestamps do not reorder events. Fields such as due dates, assignment, priority, recurrence, archive state, and synchronization conflict metadata are deferred unless a later release requires them.

## Build and dependency boundary

Compile Rust to `wasm32-unknown-unknown`. Explore a small explicit JavaScript/WASM ABI without `wasm-bindgen`, `web-sys`, `js-sys`, or `serde` initially. Use native Web Components, vanilla JavaScript, and browser APIs. Do not add a framework runtime. Any change to these constraints should state the concrete requirement that motivates it.

## Explicitly out of scope

- Handoff, Talk, Pulse, routines, and Since You Last Looked
- Accounts, real partner login, household pairing, and passkeys
- Encryption, Web Crypto integration, backend, and remote sync
- QR codes, device trust, and revocation
- Notifications, analytics, and AI processing of household content
- A general calendar or task-management system

## Completion criteria

The first coded release is complete when a user can add one simple item, see it in the UI, complete it, refresh the page, and see the reconstructed completed state; the event history is stored locally; and Rust owns event validation and state reconstruction while JavaScript owns browser integration and rendering. The workflow should be tested at the Rust domain boundary and in the browser where practical, with no claim of multi-user or synchronized behavior.

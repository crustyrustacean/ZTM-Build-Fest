# Kin v0.8.0 — Household Pairing Contract (Planning Checkpoint)

**Status:** Implemented in v0.8.0; this document is the living record for the v0.8.x incubation line.

## Product boundary

v0.8.0 will make one local-first Kin household usable by two adult members on explicitly trusted devices. Pairing establishes identity and authorization; it does not add chat, roles, assignments, analytics, notifications, or a server-side household state. Existing Item, Handoff, Talk, Pulse, Routine, and summary semantics remain unchanged until a reviewed sync contract exists.

The first capability slice is: create a household, invite one member with a short-lived one-time pairing session, accept on a second device, register a passkey for the joining member, authorize that device, inspect trusted devices, and revoke a device. Member removal, recovery after losing every authorized device, encrypted event relay, and historical re-encryption remain separate decisions.

## Identity terminology

- **Household:** stable opaque identifier for one coordination space.
- **Member:** an adult identity in the household; membership is explicit and never inferred from event activity.
- **Device:** one browser/application installation authorized for one member; replacement creates a new device.
- **Credential:** a passkey/WebAuthn credential that authenticates a member; it is not a device key or household encryption key.
- **Pairing session:** short-lived, single-use enrollment state binding inviter, invitee device, household, and transcript.

These identities must not be collapsed into one ID or represented by display names as authority.

## Required flows

1. An authenticated existing member creates a household or starts an invitation.
2. The inviter displays a high-entropy, short-lived QR/code containing only session material.
3. The recipient scans or enters it; both devices bind the same session and verify a transcript fingerprint.
4. The recipient explicitly accepts, creates or selects a passkey, and names the device locally.
5. The authorized device receives only the access needed for the household protocol.
6. Either party can cancel; expiry, cancellation, failed confirmation, replay, and wrong-device entry grant no membership or content access.
7. An existing member can list and revoke a specific trusted device. Revocation blocks future authorization; it cannot erase copied plaintext.

Adding a device for an existing member is a separate flow and must not create a second member.

## Security and recovery gates

Pairing requires a reviewed cryptographic protocol using platform Web Crypto/WebAuthn primitives or a narrowly justified audited dependency. Kin must not invent a cryptographic primitive, derive household keys from passkey assertions, put a household key in a QR code, or claim end-to-end encryption before implementation and review.

Before code is released, decide and document: session expiry and entropy, server versus local rendezvous, transcript binding and human verification, rate limiting, credential replacement/revocation, lost-device recovery, last-device recovery, device-key storage, household-key provisioning, revocation key rotation, and what history a newly authorized device may receive. A pairing code is never recovery by itself.

## Architecture boundary

Browser JavaScript owns WebAuthn, Web Crypto, QR/code presentation, session lifecycle, network transport, IndexedDB integration, focus/visibility, and secret lifetime. Rust owns validation and deterministic replay of any approved identity/membership events; it never calls browser APIs or handles DOM/network state. A relay, if approved, carries authenticated opaque protocol data and never becomes the household domain reducer.

No existing event kind is renumbered or reinterpreted. The reserved conceptual kinds in `docs/EVENTS.md` (`HOUSEHOLD_CREATED`, `MEMBER_INVITED`, `MEMBER_JOINED`, `MEMBER_REMOVED`, `DEVICE_AUTHORIZED`, `DEVICE_REVOKED`) require frozen payload layouts, authorization rules, protocol version, malformed-input behavior, duplicate/conflict handling, and migration compatibility before implementation. Do not add them speculatively to v7 histories.

## Local-first and privacy requirements

Local household actions remain useful offline. Pairing metadata is minimized, secrets are never logged, and UI errors do not disclose whether a household or member exists. The relay may observe routing metadata and timing if one is introduced; encrypted payloads do not provide anonymity. Existing local-only releases must continue to open without an account or network.

## Acceptance before tagging v0.8.0

- Frozen identity, event, ABI, storage, authorization, and recovery contracts reviewed together.
- Threat-model and cryptographic review completed; no unsupported security claim.
- Browser/Rust responsibilities and secret ownership are explicit.
- Pairing-session expiry, cancellation, replay, wrong-device, duplicate, stale, revoked-device, offline, and retry matrices are tested.
- Existing protocol v1–v7 fixtures and local households remain valid.
- Accessibility covers keyboard operation, focus, status announcements, QR/code alternatives, timeout messaging, forced colors, narrow layouts, and no secret disclosure through accessible names.

## v0.8.0 implementation record

The implementation uses a small same-origin Node service because cross-device expiry, bounded attempts, authorization and atomic membership cannot honestly be enforced by a static page. The service keeps identity state in memory during this incubation release; restart is destructive to server identity state and is an explicit limitation, not a recovery mechanism. It never receives household event content.

- Codes use 40 bits from Node's cryptographic RNG, omit ambiguous letters, expire after ten minutes, are single-use, and are stored only as HMAC-SHA-256 verifiers.
- The state machine is `Pending -> Claimed -> Confirmed`, with `Pending|Claimed -> Expired|Revoked`; terminal transitions fail and confirmation is idempotent.
- WebAuthn verifies origin, RP ID hash, user-presence/user-verification flags, challenge freshness, credential ID, ES256/RS256 signatures, and monotonic nonzero counters.
- An HttpOnly, SameSite=Strict opaque session binds member and trusted device. IDs are references, never authority by themselves.
- Claim creates only pending credential/device material. An authenticated existing adult must approve with a fresh passkey assertion before the member and device are inserted atomically.
- The household maximum is exactly two active adults. Pairing never discloses the inviter, member list, household content, or household identifier to an unapproved claimant.
- Trusted-device inspection and revocation are implemented. Revocation invalidates future service authorization but cannot erase local plaintext.
- Existing household events remain local. No content-key provisioning, encrypted sync, QR, backup, or last-device recovery is claimed.

Validation begins with `node server/pairing-service.test.mjs` and the existing Rust/Wasm/browser regression gates. Subsequent v0.8.x sections record hardening findings and evidence.
